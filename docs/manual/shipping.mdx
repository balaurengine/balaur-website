# Shipping a game

## Packs

`balaur export` compiles every script to bytecode — with the same compiler
configuration dev mode uses, so shipped bytecode is what was tested — and
bundles scripts, scenes, and the manifest into a single `.bpak`:

```bash
balaur export my-game        # writes my-game.bpak
balaur play my-game.bpak     # run from bytecode only
```

Packed runs construct no compiler and no file watcher, and no script sources
exist in the shipped build. A pack is written in sorted key order, so
exporting the same sources twice gives the same bytes, on any machine —
which makes reproducible builds and content-change checks possible.

TOML assets (animation clips and every other registered asset type) are
bundled too, and resolve by the same references, so a packed run loads them
exactly as a dev run does. Binary assets — textures, models, audio — ship in
the same pack, each verified against its SHA-256 when loaded.

Because packed execution is pure interpretation of precompiled bytecode, it
ships on platforms with JIT/codegen restrictions; CI cross-compiles the
headless engine to iOS, Android, and WebAssembly (Emscripten) on every push
to keep that true.

## Fused executables

A pack is data — it still needs an engine to run it. To ship something a
player can just open, fuse it onto a *runtime template*, the engine binary
published for each platform:

```bash
balaur export my-game --target linux-x64     # or macos-universal, windows-x64
```

The result is one executable. Fusing appends the pack to the template binary
and writes a trailer; ELF, Mach-O, and PE all ignore trailing bytes, so the
file still runs. On startup the engine reads its own executable: finding a
pack means it is a shipped game, so it boots that; finding nothing means it
is the CLI. One binary is therefore the editor, the CLI, and every game's
runtime.

The template for your own platform ships with the editor download in
`templates/`. For another platform, `balaur export` offers to download the
template from the engine's own release tag — verified against the release's
`SHA256SUMS` — into a per-user cache (`<data dir>/balaur/templates/<version>`,
never inside a project). The version pinning is deliberate: a pack must only
meet the runtime its compiler shipped with. `--download` skips the prompt and
`--no-download` forbids fetching (for CI); the manual routes still work —
drop a `balaur-runtime-*` binary into `templates/`, point `BALAUR_TEMPLATES`
at a directory, or pass `--template <file>`.

Two practical notes:

- A flat fused binary cannot be validly code-signed — appending is exactly
  what a signature cannot cover. For a signed macOS game, export a bundle:
  `balaur export my-game --target macos-universal --app` builds a `.app`
  with the pack as a sealed resource and signs it ad-hoc;
  `--sign "Developer ID Application: …"` uses a real identity.
- The exporter sets the execute bits on its output, because templates that
  came through a zip or CI artifact store usually lost theirs.

## Mobile

Mobile is the same command with a different shape of output, because neither
mobile OS runs a bare executable:

```bash
balaur export my-game --target ios       # -> my-game.app
balaur export my-game --target android   # -> my-game-android/ (an APK layout)
```

The pack rides inside the bundle as a resource — `game.bpak` beside the
executable in an `.app`, `assets/game.bpak` in an APK — and the engine reads
it from there instead of out of its own file. The project's name is written
into the `.app`'s `Info.plist`, so the home screen does not say "Balaur" for
every game exported from it.

Both come out unsigned: signing needs a certificate or keystore that is
yours, not the engine's. `scripts/assemble_apk.sh` in the engine repository
shows the sequence that turns an Android layout into an installable APK.

## Keeping the install current

`balaur update` replaces the whole install — the binary, the bundled editor
and its runtime template, which only work as a set — with the latest
published build, verified against the release's checksums. A tagged release
updates to the newest release; a nightly build follows the rolling nightly;
a source build refuses and points at git. `--check` only reports, `--tag`
picks a specific release.

## Save games

`save::write(slot, data)` stores a table per user under the platform's
user-data directory, and `save::read(slot)` brings it back; `save::slots()`
lists them and `save::remove(slot)` deletes one. A slot is a name — letters,
digits, `-` and `_` — checked rather than trusted, and a file is written
beside its target and renamed over it, so a crash mid-save cannot leave a
truncated one.

```toml
[save]
version = 3                     # what this build writes
migrate = "scripts/saves.rn"    # brings an older file forward
```

Every file is stamped with the build's `version`. Reading an older one calls
the migration script's `migrate_save(version, data)` once per version step —
1 to 2, then 2 to 3 — so a migration only ever knows how the shape changed
between two adjacent versions. A file written by a newer build is refused
rather than misread. Anything else a game keeps per user — settings, key
rebindings — goes through `engine::user_data_dir()` too, so game code never
hardcodes an OS path.

## Embedding

For a custom binary, embed the pack directly:

```rust
fn main() -> anyhow::Result<()> {
    balaur::boot_pack(include_bytes!("game.bpak"))
}
```

This route requires a Rust toolchain on the machine doing the shipping;
fused export exists so that editor users do not need one.
