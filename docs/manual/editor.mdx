# The editor

The editor is a regular Balaur project: its scripts draw the whole interface
through the `ui` module, and editing any editor script hot reloads the editor
itself. Nothing in it is privileged — every binding it uses is available to
any project.

```bash
cargo run -p balaur_cli --features window -- edit my-game
```

![The editor on examples/angrynerds: the node tree, the viewport with its 2D grid and gizmo, the inspector, and the dock tabs](/img/manual/editor_overview.webp)

## How it works

`balaur edit <project>` runs the editor with the game's path in its
arguments. The editor parses the game's scene TOML into a document model and
mirrors it as a real node subtree, so the viewport shows the actual scene and
physics builds the actual bodies (paused until play). Edits are written back
to the scene file as TOML, and every edit is undoable (`Ctrl+Z` /
`Ctrl+Shift+Z`).

**Play-in-editor** attaches the game's scripts to the mirrored nodes and
unpauses: the actual game code runs against the actual scene inside the
editor, and every run is recorded (see [Determinism](./determinism.mdx#in-the-editor)).
Stop rebuilds the mirror from the document.

## Personas

The top bar switches between five personas. Each arranges the same panels —
node tree, viewport or code, docks, inspector — around one job.

- **Scene.** The tree, the viewport with its gizmos, and the inspector
  generated from the component registry: every registered component —
  third-party plugin components included — is addable and editable with no
  editor changes. A 2D scene is detected from its components and gets a 2D
  grid, a pan-and-zoom camera, a 2D gizmo, click-picking and collider
  overlays. See [Scenes and nodes](./scenes.mdx).
- **Script.** One buffer per file with Rune highlighting, the hooks the file
  declares, and the events the node receives. Save writes to the project and
  hot reloads the code — live, while playing. Click a line number in the
  gutter to set a breakpoint; the Debugger dock shows the call frames and
  their locals, with continue and step over / into / out on `F5`, `F10`,
  `F11` and `Shift+F11`. See [Scripting](./scripting.mdx#hot-reload).
- **Animate.** The timeline over the selected clip's tracks. See
  [Animation](./animation.mdx#the-animate-persona).
- **Physics.** Bodies and colliders with their overlays. See
  [Physics](./physics.mdx).
- **Interface.** Widgets laid out over the safe area. See [UI](./ui.mdx).

## Tools

The strip beside the viewport holds Select, Move, Rotate and Scale, then two
rig tools: **Rig bone** grows and poses a skeleton, and **Polygon** edits a
skinned polygon's points, triangulation, UVs and weights. Both are described
under [Skeletons and skins](./animation.mdx#skeletons-and-skins).

## Docks, palette, themes

Seven docks sit under the viewport. **Output** is the engine's log ring
buffer, with level filters. **Problems** lists what the linter found in every
script, and a shader that would not link. **Assets** browses the project's
files. **Timeline** is the animation editor's. **Debugger** shows a paused
script's frames and locals. **Session** lists the recordings play-in-editor
made and replays one, with lanes for the input, network and log events it
holds. **Profiler** draws the last frame as a bar per stage against the
16.7 ms a 60 Hz frame has, from `engine::timings()`.

The command palette (`⌘K`) is the single overlay — nodes, commands and
personas — and the editor has a dark and a light theme. *Show input overlay*
in the palette draws the keys, buttons and pointer the game is being fed;
see [Input](./input.mdx#seeing-input).

## Driving it from the command line

The editor starts in any state you name, which is how it is tested and how
every picture in this manual was taken:

```bash
balaur edit examples/rig --offscreen --frames 100 \
  --state "anim,select:Thigh,tool:bone,shot=thigh.png"
```

`--state` is a comma list: a persona (`scene`, `script`, `anim`, `phys`,
`ui`), `select:<node>`, `tool:<id>`, `mode:<id>`, `dock:<name>`,
`zoom:<percent>`, `palette`, `light`, `play`, `input`, `shot=<file>` to
capture one frame, and `frames=<dir>` to capture every other frame into a
numbered directory.
`show:<name>` runs one of the scripted sequences behind this manual's clips,
which feed the game input through `input::feed_key`, `feed_mouse` and
`feed_mouse_button` — the same seam an automated test can use. Offscreen
frames advance on the fixed 1/60 step, so frame 90 is the same picture every
time it is asked for.

The engine repository's `scripts/showcase.sh` takes every image and clip on
this site that way and encodes the clips with ffmpeg, so a change to the
editor re-takes them all.

## Extending the editor

A plugin is a Rune file that adds docks, windows, palette commands,
inspector sections, property editors, viewport overlays and start-up states.
It goes in `editor/plugins/` to ship with the editor, or in your project's
`editor/` directory to belong to that game alone. Both are loaded at
start-up, in name order.

A plugin declares `register()`, returning what it adds, and optionally
`state()`, whose object becomes its own slice at `S.plugins.<name>`:

```rune
// mygame/editor/counter.rn
pub fn state() {
    #{ shown: -1 }
}

pub fn register() {
    #{
        docks: [#{ id: "counter", name: "Counter", draw: draw }],
        commands: [#{ label: "Count scripted nodes", icon: "Σ", run: count }],
    }
}

pub fn count(S) {
    let n = 0;
    for node in S.doc {
        if node.contains_key("script") {
            n += 1;
        }
    }
    S.plugins.counter.shown = n;
}

pub fn draw(S, k) {
    ui::label(format!("{} scripted nodes", S.plugins.counter.shown), #{
        size: 11.5, font: "mono", color: k.dim,
    });
}
```

`S` is the editor's whole state, the same object every built-in module gets:
the document (`S.doc`), the live mirror, the selection (`S.sel`), history and
the theme. The one rule is to call the editor's history recorder before
mutating the document, so undo keeps working.

Each list is optional. `docks` and `windows` take a `draw(S, k)`; `commands`
take a `run(S)`; `sections` are `draw(S, k, node)` and are drawn under the
built-in inspector; `overlays` are `draw(S)` and draw viewport lines;
`editors` map a schema datatype to `draw(S, k, target, spec, value)`, which
replaces the built-in editor for that type; `states` map a name to `run(S)`
so a plugin carries its own start-up state, and therefore its own test.

Nothing is sandboxed: a plugin runs in the editor's host with the editor's
capabilities. That is the right first cut for a tool a project writes for
itself.

## Why it is built this way

The editor dogfoods the scripting surface: everything it needs — filesystem
access, TOML parsing, scene instantiation, script reload, camera control,
debug drawing — exists as ordinary script bindings, all reusable by any
tool or game.
