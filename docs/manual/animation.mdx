# Animation

Animation is a plugin (`balaur_anim`): one asset type (`animation_clip`), one
component (`animation`), one script module (`animation`), one system. It
depends only on the engine core — and can still animate the renderer and the
UI, because tracks address properties through the component registry.

## Clips

A clip is a length, what to do with time past it (`none | loop | pingpong`),
and a list of tracks. A clip lives in its own file — referenced from the
scene — or inline in the scene node; a library file holds several clips under
`[clips.<name>]`, addressed `file.toml#name`:

```toml
# animations/platform.toml
type = "animation_clip"

[clips.patrol]
length = 4.0
loop = "pingpong"

[[clips.patrol.tracks]]
property = "position"      # position | rotation_euler | rotation | scale | <component>/<property>
interp = "linear"          # step | linear | cubic
keys = [
  { t = 0.0, value = [-2.5, 0.25, -2.0] },
  { t = 4.0, value = [-2.5, 0.25, 2.0], ease = "in_out_sine" },
]

[[clips.patrol.tracks]]
keys = [{ t = 4.0, call = "on_reached_end" }]   # a method track
```

```toml
# in the scene
[nodes.animation]
library = "animations/platform.toml"
autoplay = "patrol"
```

A track drives the transform or any registered component's property
(`shape3d/color`, `shape2d/radius`, `widget/x`) — third-party plugin components
animate the day they are registered, with no animation-plugin changes. A
track with no `property` is a method track: its keys call a method on the
node's script. Rotation keys are authored as euler radians and interpolated
as quaternions; a `rotation` track takes the quaternion itself, which is what
an imported model's clips hold.

## The script module

```rune
animation::play(this.node, "hop", #{ speed: 1.0 });
animation::pause(this.node);   // resume continues; stop ends
animation::queue(this.node, "wave");

pub fn on_reached_end(this) {   // called by the clip's method track
    // ...
}
```

Plus `seek`, `time`, `current`, `is_playing`, `just_finished`, and `define`
for building a clip from an object at run time. A tween is asked about
separately, with `is_tween_running(handle)`.

## Tweens

A tween is a clip generated on the spot, from the values the node has now,
run through the same sampler and the same fixed step:

```rune
animation::tween(this.node, #{
    steps: [
        #{ property: "position",   to: [0.0, 3.0, 0.0],      duration: 0.5, ease: "out_back" },
        #{ property: "shape3d/color", to: [1.0, 0.0, 0.0, 1.0], duration: 0.5, parallel: true },
        #{ call: "on_landed" },
    ],
});

animation::tween_to(this.node, "position", [0.0, 9.0, 0.0], 0.2, "linear");   // the one-step shorthand
```

Steps run in order; `parallel: true` joins a step to the one before it. `to`
is absolute, `by` relative, `from` explicit, `target` tweens another node,
and `interval` and `call` sequence among the property steps. The spec is
data, so a tween is serialisable — the editor can author one and it hot
reloads. Easing is twelve transitions in four modes with Godot's names and
shapes, so ported curves behave.

The timeline's lanes are the selected clip's tracks, the ruler scrubs the
node's own player, and preview goes through the engine's parser, so what the
editor shows is what ships. A clip lives inline in the scene or in its own
file; *Save as file* and *Make inline* convert between the two exactly.
Keying a bone writes a rotation track on its character's clip, and a skinned
polygon deforms as the clip plays.

## Skeletons and skins

A bone is a node with a rest pose (`bone2d` in 2D, `bone3d` in 3D), and a
skin is a `polygon` — a textured 2D polygon whose mesh carries bone weights.
A rig needs no new animation machinery: a clip on the character keys its
bones by path.

```toml
[[nodes]]
name = "Thigh"
parent = "n_hip"
position = [0, 0.85, 0]
bone2d = { rest_position = [0, 0.85], rest_rotation = 0.0 }

[nodes.polygon]                       # on a sibling node
texture = "art/limb.png"
skeleton = ".."                       # the rig root; bones are its descendants

[nodes.polygon.mesh]                  # a `mesh` asset, inline
positions = [[-0.4, 0], [0.4, 0], [0.4, 0.85], [-0.4, 0.85]]
[[nodes.polygon.mesh.skin.bones]]
path = "Hip/Thigh"
weights = [0, 0, 1, 1]
```

The outline is ear-clipped; `internal` vertices and hand-drawn `polygons`
control the triangulation, and UVs default to the texture centred on the
node at `pixels_per_unit`. Skinning runs on the GPU from a joint palette the
engine computes from the scene tree — a headless run computes the same
palette, so bones are part of the determinism digest.

![A polygon's inspector: vertices, drawn polygons, bones and brush](/img/editor/component_limb.webp)

The `skeleton` module has Godot's two rest-pose verbs and a query:
`skeleton::apply_rest(node)` returns a rig to its rest pose,
`skeleton::overwrite_rest(node)` makes the current pose the rest pose, and
`skeleton::bones(node)` lists the bones under a node.

In the editor, the **Rig bone** tool draws bones as diamonds in 2D and
octahedra in 3D: click one to select it, drag to pose it, and *+ bone* grows
a child from the selection. The inspector's Skeleton section has the two
rest-pose verbs. The **Polygon** tool edits a `polygon` component's mesh in
four modes — *Points* places outline and internal vertices, *Polygons* draws
the triangulation by hand, *UV* places the points over the texture, and
*Weights* paints bone influence with a brush — and the polygon stays skinned
while you edit it.

### Modifiers

A `modifier2d` component runs after the clip every frame. `look_at` turns one
bone toward a target node; `two_bone_ik` solves a root, middle and tip chain
so the tip reaches the target, with `flip` choosing the bend side.

```toml
[nodes.modifier2d]
kind = "two_bone_ik"
bone = "Shoulder"
target = "Target"
```

### 3D rigs

3D rigs come from files rather than tracing:

```bash
balaur import model.glb --project my-game
```

copies the model under `models/`, writes its joint hierarchy as a scene with
`bone3d` rest poses and one `mesh` node, and its animations as a clip library
— all TOML the editor edits. A `.gltf` with its `.bin` and textures beside it
works the same way. The mesh is skinned every frame from the same scene tree,
so it animates through the same clips, and the same rest verbs and bone
gizmos apply.

The joint palette is computed from that scene tree and handed to a vertex
shader, so a 3D rig deforms on the GPU and the mesh's buffers are left alone.
A node that names a `material` asset, or a frame drawn under a shader channel
view, keeps the CPU path instead: those shaders draw against
`package::mesh` and know nothing about a palette. Both compute the same
blend — the shader's is `@const`, so a headless test holds it to the CPU
reference without a GPU. `examples/rig` is one figure: a skinned body swung by a clip, with an arm
branching off its top bone that reaches on two-bone IK;
`examples/rig3d` is a column imported this way.

## Deterministic, and scheduled deliberately

Playback advances on its own fixed 1/60 accumulator — the sampler never sees
a variable dt — and every transcendental (easing, euler↔quaternion, slerp)
is computed on bit-identical `libm` implementations, so an animation is the
same on every platform.

The system runs after the script tick, so `animation::play()` takes effect the
same frame, and before physics reads transforms — so an animated kinematic
platform pushes whatever stands on it with no extra wiring. `examples/hello`
demonstrates exactly that, and the editor's Animate persona edits the same
clip files.
