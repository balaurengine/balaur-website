# Input

- The windowed backend pumps OS events into one snapshot per frame, and
  scripts read that snapshot through the `input` module.
- Headless runs read neutral state.
- The whole frame's input is one snapshot, so recording it per tick is all a
  replay system needs.

## Actions

A game asks for `"jump"`, not for `Space`.

```toml
[input.actions]
jump = ["Space", "gamepad:South"]
move_x = ["keys:A,D", "axis:LeftStickX"]
fire = ["mouse:left"]
```

```rust
if input::action_just_pressed("jump") { /* ... */ }
let x = input::action_value("move_x");   // -1 to 1
```

- An action takes any number of keys, buttons, sticks or key pairs.
- `action_value` runs -1 to 1: a key answers 0 or 1, a stick or `keys:A,D` the
  whole range.
- `action_pressed`, `action_just_pressed` and `action_just_released` are the
  edges.
- `input::bind(name, bindings)` rebinds an action and saves it to the user
  data directory. `reset_bindings` goes back to what the project declared.
- Actions are derived from the raw snapshot every frame, so a recording holds
  the keys pressed and a replay reproduces the actions from them.

## Keyboard and mouse

```rune
if input::just_pressed(input::KEY_SPACE) { /* ... */ }
if input::is_mouse_down(input::MOUSE_LEFT) { /* ... */ }
let (mx, my) = input::mouse_position();
```

`is_down`, `just_pressed` and `just_released` cover keys by named constant.
The mouse adds position, per-frame delta, button edges and scroll delta.

## Gamepads

```rune
for pad in input::gamepads() {
    if input::gamepad_just_pressed(pad, input::PAD_SOUTH) { /* ... */ }
    let x = input::gamepad_axis(pad, input::AXIS_LEFT_STICK_X);
}
```

- `input::gamepads()` lists the connected pads, and every query takes a pad id
  and a named constant.
- Buttons are `PAD_*`, axes `AXIS_*` (sticks, triggers, d-pad).
- `input::gamepad_name(pad)` names the hardware.

## Rumble, motion and the touchpad

```rune
let turn = input::gamepad_gyro(pad);          // radians per second
let tilt = input::gamepad_acceleration(pad);  // g, with gravity in it
for touch in input::gamepad_touches(pad) {
    // touch.x and touch.y run 0 to 1 across the surface
}
```

| Call | What it does |
| --- | --- |
| `gamepad_rumble(pad, #{ strong, weak, duration })` | Runs the two motors at 0 to 1 for that many seconds; answers whether it started |
| `gamepad_stop_rumble(pad)` | Cuts one short |
| `gamepad_can_rumble(pad)` | Whether there are motors at all |
| `gamepad_gyro`, `gamepad_acceleration`, `gamepad_touches` | A PlayStation pad's motion and touchpad, decoded from its own HID reports over USB or Bluetooth |

A pad with no gyroscope or touchpad reads zero and an empty list, the answer
an absent pad gives. All of it lands in the recorded snapshot, so a replay
reproduces a motion-controlled session exactly.

## Touch

- `input::touches()` returns the fingers on the screen as `#{ id, x, y }`,
  oldest first, with `touches_started()` and `touches_ended()` for the edges.
- A finger is also a left click, so every widget kind works on a phone.
  `emulate_touch_from_mouse` does the reverse and makes a held mouse button a
  finger, which is how a desktop drives touch code.

```toml
[input]
emulate_mouse_from_touch = true   # the default
emulate_touch_from_mouse = false  # the default
```

## Touch controls

A `touch_button` presses an action while a finger is on it. A `touch_stick`
pushes one action per axis. The game reads the action, so the script that
answers a keyboard answers a phone.

```toml
[nodes.touch_stick]
action_x = "move_x"
action_y = "move_y"        # 1 pushed away from the player, as a gamepad reads
anchor = "bottom_left"
offset = [130.0, -130.0]   # design pixels to the centre, y down
radius = 90.0

[nodes.touch_button]
action = "jump"
anchor = "bottom_right"
shape = "circle"
```

- **They feed, they are not bound.** An action bound to Space gains the
  button as a second source, and the furthest from rest wins. An action no
  manifest declared still answers.
- **Placed against the screen.** `anchor` and `offset` in design pixels,
  inside the safe area. In the editor they sit in the viewport, and only while
  the game plays.
- **Hidden without a touch screen.** `visibility = "touchscreen"` is the
  default: a phone, a touch browser, or a project with
  `emulate_touch_from_mouse` shows them. `"always"` shows them everywhere.
- **The finger keeps what it grabbed.** A thumb that slides off a button
  mid-jump still holds it. `recenter = true` puts the stick under the thumb
  that found it, and `deadzone` holds a resting thumb at zero.
- **Components, not widgets.** They are hit-tested inside the tick, so they
  run headless, land in the digest and replay exactly.
- `ui::wants_pointer()` says whether a widget took this frame's finger, so a
  tap on a HUD button does not also fire the shot behind it.

## Gestures

```rune
if let Some(scale) = input::pinch().get("scale") { zoom *= scale; }
let pan = input::pan();                 // #{ x, y }, two fingers or more
if let Some(dx) = input::swipe().get("x") { /* a unit direction */ }
if input::long_press().get("x").is_some() { /* once per hold */ }
```

| Call | Answers |
| --- | --- |
| `pinch()` | `#{ scale, x, y }` while two fingers move apart or together; `scale` is against last frame |
| `pan()` | `#{ x, y }`, the average movement of every finger down |
| `swipe()` | `#{ x, y, speed }` on the frame a finger that travelled far enough lifts |
| `long_press()` | `#{ x, y }` once, when a still finger has held long enough |

Each is derived from the recorded fingers and the fixed step, so a replay
reproduces it, and each answers empty with nothing happening. `swipe_pixels`,
`long_press_seconds` and `long_press_slop` in `[input]` set the thresholds.

## The on-screen keyboard

- A focused `field` raises the system keyboard on iOS and Android.
- `input::keyboard_height()` is how much of the screen it covers, in pixels
  from the bottom: read from UIKit, the Android activity or the page, and
  recorded.
- `avoid_keyboard = true` on a root widget measures the bottom of the screen
  from the top of the keyboard, so a form or a chat bar stays above it.

## Dropped files

`input::dropped_files()` returns the paths of files dropped onto the window
this frame, which is how a tool accepts a drag and drop.

## Feeding input from a script

`feed_key`, `feed_mouse`, `feed_mouse_button`, `feed_touch(id, x, y, phase)`
and `feed_action(name, value)` put input into the frame as if a device had
reported it. A test, a showcase or an automation client drives a game with
them, and a fed frame records and replays like a real one.

## Seeing input

- The editor's input overlay draws what the game is being fed this frame. A
  chip per key and mouse button held, the actions they drive, a cursor at the
  pointer, a ring spreading from every press.
- It reads the same snapshot the game reads, so during a replay the cursor
  follows the recording rather than your hand.
- Turn it on from the command palette (*Show input overlay*), or start the
  editor with `--state input`.
- The actions come from the game's own `project.toml`. The editor is itself a
  Balaur project, so it declares the game's actions when it opens one, and
  without that every action a played game asked for would read zero.
