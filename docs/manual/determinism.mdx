# Determinism

Cross-platform determinism is a core feature: identical inputs must produce
bit-for-bit identical simulation on every platform. This is what makes
replays, lockstep networking, and "did the content change?" checks possible.

## Engine measures

- Rapier's `enhanced-determinism` feature is enabled workspace-wide, for both
  the 3D and 2D worlds.
- Physics and animation step on one app-owned fixed 60 Hz accumulator
  (`FixedUpdate`), never the variable frame delta.
- Transcendentals on a simulation path — animation easing, euler↔quaternion
  conversion, slerp — are computed on the `libm` crate rather than the
  platform's math library, which differs across OSes.
- Network completions enter the simulation once per tick, at the start of the
  frame, in arrival order — never from an I/O thread — so a recorded session
  replays without touching the network, logins and retries included.
- Order-sensitive Rust iteration uses an insertion-ordered map type, never
  bare `HashMap` iteration.
- Scene instantiation order and scene-key application order are
  deterministic.
- Rendering and audio are pure observers of simulation state: headless,
  offscreen, and windowed runs compute exactly the same simulation.
- Input is captured once per frame into a snapshot, so recording it per tick
  is all a replay system needs.
- Dev-mode and shipped bytecode come from one compiler configuration.
- A repository test asserts two runs match bit for bit.

## Scripting and determinism

Rune numbers are IEEE-754 doubles and 64-bit integers that never mix;
`+ - * /` and `sqrt` are exactly specified and reproducible everywhere, and
the VM is a single-threaded interpreter with no native codegen, so evaluation
order is fixed. The known hazards are addressed directly:

| Hazard | Status |
| --- | --- |
| `sin`, `cos`, `exp`, `pow`, ... call the platform libm, which differs across OSes | The engine's `math` module (`math::sin`, `math::pow`, `math::PI`, ...) is implemented on pure-Rust `libm` and is bit-identical everywhere. Simulation code calls `math::*`; Rune's own float methods stay the platform's |
| A random source seeded from entropy | Rune has none of its own; the `rng` module (`rng::seed/random/range/int`) is an engine-owned seeded PCG32 stream with a fixed default seed, so a fresh run reproduces by construction |
| Iteration order over an object (`for (k, v) in obj`) is the hash map's, not insertion order | Rule: simulation-affecting iteration uses lists or sorted keys |
| Wall-clock time leaking into simulation | Simulation goes in `fixed_update(dt)`, which runs on the 60 Hz step with a constant dt; `update(dt)` is for presentation. Use `engine::tick()` for time |
| Hot reload mid-session | Changing code changes behaviour; turn it off for a run you intend to verify |

## Checking, recording, replaying

Pin the step and write a hash of the world each tick:

```bash
balaur run my-game --fixed-tick --trace-digest run-a.txt
```

Two runs that differ parted at the first differing line; run it on two
machines and `diff` the files. That is the whole cross-platform check, and
CI does it for every example on Linux, macOS and Windows.

A recorded session stores input, not state — minutes of play is kilobytes —
and replaying it re-checks every tick:

```bash
balaur run my-game --fixed-tick --record session.blr
balaur replay session.blr --verify          # stops at the first tick that disagrees
balaur replay session.blr --entries-at 25   # that tick, one digest per node and component
```

Network replies are recorded too, and a replay never touches the network.
Rollback works the same way in the other direction: a snapshot restores a
tick and the deterministic simulation re-runs the same inputs forward. The
engine's [determinism guide](https://github.com/balaurengine/balaur/blob/main/docs/DETERMINISM.md)
has the rules of thumb and the hazards that remain your problem.

## Verified, not asserted

The demo project's ball touches down at the same simulation time in headless
and windowed runs, and from the exported pack. Pack export writes in sorted
key order, so exporting the same sources twice gives the same bytes on any
machine — CI exports every example twice per platform and compares digests
across the matrix.
