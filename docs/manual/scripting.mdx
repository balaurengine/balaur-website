# Scripting

Scripts are [Rune](https://rune-rs.github.io/) — `.rn` files attached to
nodes in a scene. Rune reads like Rust without types; the
[Rune book](https://rune-rs.github.io/book/) covers the language itself.

## The model

A script declares lifecycle functions — `init`, `update(dt)`,
`fixed_update(dt)`, `draw_ui`, `on_free`, `hot_reload` — as free functions
taking the instance first. The engine makes one instance per attached node,
hands it back on every call as `this`, and puts the owning node on
`this.node`. An object handed into a Rune function is mutated in place, so
what a script writes to `this` is what the host reads next frame.

```rust
// scripts/spinner.rn
pub fn init(this) {
    this.angle = 0.0;
}

pub fn update(this, dt) {
    this.angle += dt;
    this.node.set_rotation_euler(0.0, this.angle, 0.0);
}

pub fn fixed_update(this, dt) {}   // the fixed 60 Hz step, before physics
pub fn draw_ui(this) {}            // immediate-mode UI, once per frame
```

`update` runs once per frame with the measured frame time; `fixed_update`
runs on the fixed 60 Hz step, before physics, and is where simulation
belongs. See [Determinism](./determinism.mdx).

`project.toml` names the language with `language`; it defaults to `"rune"`,
and any other value is an error.

## Modules

Subsystems declare their bindings once against a language-neutral seam
(`balaur_script`), and scripts reach them as modules with `::`: `engine`,
`scene`, `log`, `input`, `rng`, `math`, `physics`, `physics2d`,
`physics3d`, `render`, `audio`, `ui`, `animation`, `skeleton`, `assets`,
`http`, `websocket`, `gamend`, `task`, `debugger`, `fs`, `toml`, `json`
and `script`. The complete surface — every function and constant — is in
the [script modules reference](/docs/reference/modules), which is generated
from a booted engine so it cannot drift.

```rust
let t = engine::time();
let ball = scene::get_node("World/Ball");
physics3d::add_body(this.node, physics3d::BODY_DYNAMIC);
```

Values a binding accepts are named rather than spelled: `input::KEY_SPACE`,
`input::MOUSE_LEFT`, `physics3d::BODY_DYNAMIC`, `ui::ANCHOR_TOP_LEFT`.

Node operations are methods on a node value: `this.node.position()`,
`node.get_node("../Target")`, `node.set_component("widget", w)`. A call
that returns several values returns a tuple — `let (text, changed) =
ui::text_field(...)` — while a vector is one value with fields:
`this.node.position().y`.

Each component a node can carry is also a field on the node, and that field
is a handle whose methods are the driving module's functions with the node
filled in: `this.node.body2d.apply_impulse(x, y)` is
`physics2d::apply_impulse(this.node, x, y)`. Every handle has `get()`,
`set(table)`, `has()` and `remove()` too. The [component
reference](/docs/reference/components) lists the methods per component.

```rust
let body = this.node.body2d;
body.apply_impulse(0.0, 12.0);
if body.linear_velocity().0 > 5.0 {
    body.set_linear_velocity(5.0, 0.0);
}
```

Tables are objects, `#{ kind: "ball", radius: 0.5 }`; lists are `[1, 2]`;
nothing is `()`. Integers and floats never mix, so anything a binding takes
as a float is written `0.0`.

## Script files as modules

`mod name;` at the top of a script pulls in `name.rn` beside it — from disk
in a dev run, from the pack when shipped — and its items are reached as
`name::item`:

```rust
mod util;   // scripts/util.rn

pub fn update(this, dt) {
    this.speed = util::clamp(this.speed + dt, 0.0, 10.0);
}
```

`script::require("lib.rn")` loads a file at run time instead and returns
its functions in an object. Both hot reload in place: a module object held
since `init` sees the new code after a save.

## Errors

A binding that fails raises an error and the call ends there. Wrap a call
that may legitimately fail in `script::attempt`, which returns `(ok, value)`
— the result, or the error message:

```rust
let (ok, clip) = script::attempt(|| assets::load("animations/missing.toml"));
if !ok {
    log::warn(format!("no clip: {}", clip));
}
```

## Events

There are no `connect`-style signals. The engine calls methods a script
declares by name — `on_animation_finished(name)` from an animation, a
widget's `on_click`, `on_response(r)` from an HTTP request — so a handler
reads exactly like `update(dt)` does. Most events also have a polling twin
(`input::just_pressed`, `animation::just_finished`): an event is a
frame-scoped snapshot, not a subscription.

An asynchronous operation can also be awaited in sequence. An entry point
declared `async` suspends on `task::wait` and resumes when the result enters
the simulation at the start of a later tick:

```rust
pub async fn init(this) {
    let r = task::wait(http::request("https://example.com")).await;
    log::info(format!("{} {}", r["status"], r["body"]));
}
```

See [Networking](./networking.mdx) for the delivery model.

Scripts invoke each other the same way the engine does:
`node.call("method", args...)` calls a method on another node's script
instance by name.

## Hot reload

The host watches the project directory. On save, the file is recompiled; a
compile error keeps the previous unit running and is reported once. Rune
compiles to an immutable unit, so there is nothing to patch: the new unit
replaces the old one, instances keep their state objects, and the next call
resolves against the new code. Measured save-to-live latency is
file-watcher latency, a few milliseconds. The optional `hot_reload(this)`
hook lets a script migrate the shape of its state.

## Debugging

A script can be paused on a breakpoint and stepped. In the editor's Script
persona, click a line number to set a breakpoint and run the scene; the
Debugger dock shows the call frames and their locals, with continue and
step over / into / out on `F5` / `F10` / `F11` / `Shift+F11`. The same
controls are the `debugger` script module, so a tool can drive them:

```rust
debugger::set_breakpoints("scripts/ball.rn", [12, 30]);
let pause = debugger::paused();         // (), or the pause: reason, line, frames
debugger::resume(debugger::STEP_OVER);  // CONTINUE | STEP_OVER | STEP_INTO | STEP_OUT
```

A script that throws normally logs the error and the engine carries on.
Turning on break on error stops at the line that threw instead, with the
frames and locals still there to read:

```rust
debugger::set_break_on_error(true);
```

It is off by default because it puts every synchronous call through the
stepping executor, which is otherwise used only where you have set a
breakpoint. The Debugger dock has the same switch. An error pause cannot be
continued — the call is over — so letting go of one drops it and finishes
the tick it interrupted, whichever step button you press.

Two further limits: an async entry point (one that uses `task::wait`) runs
as a future and cannot be paused, so a breakpoint inside one is let through;
and locals are a frame's named arguments, since Rune keeps no names for its
other slots.

## Determinism in scripts

Straightforward simulation code is deterministic by construction: the
engine's `math` module (`math::sin`, `math::pow`, `math::PI`, ...) is
`libm`-backed and bit-identical on every platform, and `rng` is an
engine-owned seeded stream. Simulation goes in `fixed_update`. See
[Determinism](./determinism.mdx) for the rules.
