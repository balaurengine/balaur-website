# Scripting

Scripts are [Rune](https://rune-rs.github.io/): `.rn` files attached to
nodes in a scene. Rune reads like Rust without types; the
[Rune book](https://rune-rs.github.io/book/) covers the language itself.

## The model

A script declares lifecycle functions: `init`, `update(dt)`,
`fixed_update(dt)`, `draw_ui`, `on_free`, `hot_reload`, as free functions
taking the instance first. The engine makes one instance per attached node,
hands it back on every call as `this`, and puts the owning node on `this.node`.
Rune mutates an object in place, so what a script writes to `this` is what the
host reads next frame.

```rune
// scripts/spinner.rn
pub fn init(this) {
    this.angle = 0.0;
}

pub fn update(this, dt) {
    this.angle += dt;
    this.node.set_rotation_euler(0.0, this.angle, 0.0);
}

pub fn fixed_update(this, dt) {}   // the fixed 60 Hz step, before physics
pub fn draw_ui(this) {}            // immediate-mode UI, once per frame
```

`update` runs once per frame with the measured frame time; `fixed_update` runs
on the fixed 60 Hz step, before physics, and is where simulation belongs. See
[Determinism](./determinism.mdx).

`project.toml` names the language with `language`. It defaults to `"rune"`, and
any other value is an error.

## Exported properties

A script says which of its values a scene may tune by returning their
defaults from `exports`:

```rust
pub fn exports() {
    #{ speed: 2.0, clockwise: true }
}
```

The node's `script` key then takes a table beside the string form, setting
only what it overrides:

```toml
[nodes.script]
source = "scripts/spinner.rn"

[nodes.script.props]
speed = 3.5
```

The defaults are written onto the instance, the node's `props` over them, and
only then is `init` called. The inspector writes an override only where the
value differs from the default, so changing a default in the file reaches every
node that never overrode it. `node.attach_script(path, props)` is the same
thing at run time.

## Modules

Subsystems declare their bindings once against a language-neutral seam
(`balaur_script`), and scripts reach them as modules with `::`: `engine`,
`scene`, `log`, `input`, `rng`, `math`, `physics`, `physics2d`, `physics3d`,
`render`, `audio`, `ui`, `animation`, `skeleton`, `assets`, `http`,
`websocket`, `gamend`, `events`, `task`, `debugger`, `fs`, `toml`, `json` and
`script`.
Every function and constant is in the
[script modules reference](/docs/reference/modules), generated from a booted
engine so it cannot drift.

```rune
let t = engine::time();
let ball = scene::get_node("World/Ball");
physics3d::add_body(this.node, physics3d::BODY_DYNAMIC);
```

Values a binding accepts are named rather than spelled: `input::KEY_SPACE`,
`input::MOUSE_LEFT`, `physics3d::BODY_DYNAMIC`, `ui::ANCHOR_TOP_LEFT`.

Node operations are methods on a node value: `this.node.position()`,
`node.get_node("../Target")`, `node.set_component("widget", w)`. A call
returning several values returns a tuple: `let (text, changed) =
ui::text_field(...)`, while a vector is one value with fields:
`this.node.position().y`.

Each component a node can carry is also a field on the node, and that field is
a handle whose methods are the driving module's functions with the node filled
in: `this.node.body2d.apply_impulse(x, y)` is `physics2d::apply_impulse(this.node, x, y)`.
Every handle also has `get()`, `set(table)`, `has()` and `remove()`. The
[component reference](/docs/reference/components) lists the methods per
component.

```rune
let body = this.node.body2d;
body.apply_impulse(0.0, 12.0);
if body.linear_velocity().0 > 5.0 {
    body.set_linear_velocity(5.0, 0.0);
}
```

Tables are objects, `#{ kind: "ball", radius: 0.5 }`; lists are `[1, 2]`;
nothing is `()`. Integers and floats never mix, so anything a binding takes
as a float is written `0.0`.

## Script files as modules

`mod name;` at the top of a script pulls in `name.rn` beside it, from disk
in a dev run, from the pack when shipped, and its items are reached as
`name::item`:

```rune
mod util;   // scripts/util.rn

pub fn update(this, dt) {
    this.speed = util::clamp(this.speed + dt, 0.0, 10.0);
}
```

`script::require("lib.rn")` loads a file at run time instead and returns its
functions in an object. Both hot reload in place: a module object held since
`init` sees the new code after a save.

## Errors

A binding that fails raises an error and the call ends there. Wrap a call
that may legitimately fail in `script::attempt`, which returns `(ok, value)`
: the result, or the error message:

```rune
let (ok, clip) = script::attempt(|| assets::load("animations/missing.toml"));
if !ok {
    log::warn(format!("no clip: {}", clip));
}
```

## Events

There are no `connect`-style signals. The engine calls methods a script
declares by name: `on_animation_finished(name)` from an animation, a widget's
`on_click`, `on_response(r)` from an HTTP request, so a handler reads exactly
like `update(dt)`. Most events also have a polling twin
(`input::just_pressed`, `animation::just_finished`): an event is a frame-scoped
snapshot, not a subscription.

An `async` entry point suspends on `task::wait` and resumes when the result
enters the simulation at the start of a later tick:

```rune
pub async fn init(this) {
    let r = task::wait(http::request("https://example.com")).await;
    log::info(format!("{} {}", r["status"], r["body"]));
}
```

See [Networking](./networking.mdx) for the delivery model.

Scripts invoke each other the same way the engine does:
`node.call("method", args...)` calls a method on another node's script
instance by name: one target, now, when you hold the node.

For the other shape: something happened and the emitter does not know who
cares. There is `events`:

```rune
this.node.emit("hit", #{ damage: 3 });          // from this node

events::subscribe(this.node, "hit", enemy);     // only that enemy's
events::subscribe(this.node, "hit");            // every emitter's
pub fn on_hit(this, payload) {}                 // on_<name>, whichever it was
```

Delivery is the top of the next frame's update, in emission then subscription
order, so a handler never runs inside the call that emitted. Naming the
emitter is also what keeps a hundred emitters of `hit` from waking a hundred
handlers each: it is part of the key, so delivery is a lookup. `events::emit`
is the same without an emitter, and `events::emitted(name)` /
`events::emitted_from(node, name)` are the polling twins.

## Hot reload

<Clip name="scripting_live" alt="A value changed and saved while the scene runs, then a breakpoint stepped in the Debugger dock" />

The host watches the project directory and recompiles a file on save. Rune
compiles to an immutable unit, so there is nothing to patch: the new unit
replaces the old one, instances keep their state objects, and the next call
resolves against the new code. Save-to-live latency is file-watcher latency, a
few milliseconds. The optional `hot_reload(this)` hook lets a script migrate
the shape of its state.

A save that does not compile puts the compiler's own diagnostic: file, line,
column and caret, in the editor's Output dock, and the previously compiled
code keeps running. Rune resolves module paths at compile time, so a misspelled
engine call is caught on save rather than when the line finally runs.

## Debugging

In the editor's Script persona, click a line number to set a breakpoint and
run the scene. The Debugger dock shows the call frames and their locals, with
continue and step over / into / out on `F5` / `F10` / `F11` / `Shift+F11`. The
same controls are the `debugger` script module, so a tool can drive them:

```rune
debugger::set_breakpoints("scripts/ball.rn", [12, 30]);
let pause = debugger::paused();         // (), or the pause: reason, line, frames
debugger::resume(debugger::STEP_OVER);  // CONTINUE | STEP_OVER | STEP_INTO | STEP_OUT
```

A script that throws logs the error and the engine carries on. Break on error
stops at the line that threw instead, with the frames and locals still there to
read:

```rune
debugger::set_break_on_error(true);
```

It is off by default because it puts every synchronous call through the
stepping executor, otherwise used only where a breakpoint is set. The Debugger
dock has the same switch. An error pause cannot be continued: the call is over
, so letting go of one drops it and finishes the tick it interrupted, whichever
step button you press.

Two further limits: an async entry point (one using `task::wait`) runs as a
future and cannot be paused, so a breakpoint inside one is let through; and
locals are a frame's named arguments, since Rune keeps no names for its other
slots.

## Determinism in scripts

Simulation code is deterministic by construction: the `math` module
(`math::sin`, `math::pow`, `math::PI`, ...) is `libm`-backed and bit-identical
everywhere, and `rng` is an engine-owned seeded stream. Simulation goes in
`fixed_update`. See [Determinism](./determinism.mdx) for the rules.
